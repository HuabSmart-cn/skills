# 飞书口播稿

这个 Skill 负责三件事：统一生成口播稿格式、按用户意图暂存临时稿，以及在用户明确确认后写入正式的飞书知识库目录。在拍视频文案项目为洪峰华本人写稿，或用户明确要求洪峰华、华彬 AI 工位及已明确指向本人的“我的风格”时，先读取 `hongfenghua-ai-oral`；其他作者不套用。最后由 `human-writing` 优化中文，个人风格的修辞适配按其主文件的专属分支执行。飞书目录和写入流程遵循 `lark-wiki` 与 `lark-doc` 的规则。

## 核心边界

- 先生成草稿，默认只在对话中呈现，不写飞书。
- 用户明确说“放临时”“暂存”“先存一下”“不转正式”等，才把当前版本写入 `自媒体口播文案 → 临时口播稿-稿件`。临时保存不等于正式确认。
- 只有用户明确说“确认”“可以入库”“放到飞书”“正式保存”等，才把最终版本新建到 `自媒体口播文案 → 7-8 月口播稿`。仅说“看看”“改一下”“这版怎么样”不算正式确认。
- 临时稿与正式稿分开建文档。正式确认时以最终确认内容为准，在正式目录新建文档；不要自动把临时文档移动、删除或覆盖，除非用户另行明确要求。
- 临时或正式新文档都不能放到知识库根目录，不能覆盖《口播稿模板》或已有口播稿。
- “发布前自检（由 AI 录入时评判填写）”必须按当前模板原样保留。不要把它改成录制者自检清单，也不要擅自增加录音时长、剪辑或发布检查项到这一节。
- 交付给用户或写入飞书的正文到模板最后一项结束为止。不要在文档末尾追加“已按模板保留”“本次未上传”“验证结果”等助手说明，这些只放在对话回复里。
- 不捏造用户经历、现场、对白、数据或案例。事实型内容区分已核验来源、外部材料和作者判断。
- 口播正文以“我”为主体，写成自然分享和解释，不写营销号开场、夸张悬念或连续口号。需要时调用 `human-writing` Skill。

## 先过结构关，再做口语化

- 外部材料的编号、小标题和论证顺序只是后台素材，不是口播提纲。先找一个能驱动整篇的真实问题、动作、矛盾或判断变化，再决定哪些观点需要进入正文。除非用户明确要求盘点或教程，不按原材料的条目数量逐项缩写。
- 第一人称必须有真实位置。优先使用用户提供的行动、疑问、判断和口述节奏；只有观点没有亲历时，就写诚实的观点稿，不补“我见过”“我听说过”或虚构现场。
- 口语感来自思考怎样往前走，不来自填充词。不要用“其实”“这么说吧”、粗口、括号插话和故意啰嗦掩盖议论文骨架。
- 不让每段重复“观点、解释、例子、建议、金句收尾”。段落长度和作用可以不同，有些地方只交代一件事，有些地方承认疑问或继续追问。高强度总结句只留在确有材料支撑的位置。
- 用户提供口述转写时，以转写为主要声音材料，保留他的用词和关注顺序，再修事实、逻辑和赘余。没有转写时，先在内部形成一版不带编号和小标题的松散口述路径，再整理成模板正文。
- 完稿后暂时去掉编号和小标题朗读。正文接不下去，或仍能明显听成对原材料的逐条回应，就重写结构，不能只改词语和句长。

## 传播性自检：断言、重复、形象

把这三个概念作为口播稿的传播检查工具，不把它们当成替代事实、论证和录制验证的公式。

- 断言：先用一两句明确、可复述、允许观众反驳的判断钉住方向。复杂问题可以压缩成中心判断，但不要把局部条件伪装成普遍因果；依据不足时标明这是作者判断。
- 重复：选定一个核心句或稳定词组，在开头、关键转折和必要的收束处重复。每次重复都要推进新的事实、例子或应用，避免机械复读，也不要为了呼应而在结尾重新摘要全文。
- 形象：把抽象观点落到具体的人、动作、场景、物件或可观察的结果上，让观众能在脑中看见它。只使用用户提供或已经核验的材料，不补写用户没经历过的现场；形象必须服务于判断，不能只做装饰性比喻。
- 完成初稿后，内部检查观众听一遍能否说出中心判断，过几天遇到类似问题能否调用这句话。记不住时，先调整断言、重复和形象的组合，再考虑增加解释。

遇到高传播内容时，从生产者视角做一次轻量拆解：它的中心断言是什么，哪个词或句式被重复，哪一个具体形象让观点变得可见，三者怎样共同降低理解和复述成本。只吸收可迁移的方法，不照搬原文故事、粗口、案例或未经核验的因果。

## 默认格式

生成或写入前读取 [template.md](references/template.md)。至少保留这些栏目，顺序不变：

1. 主题信息
2. 推荐标题及副标题
3. 视频标签/关键词
4. 口播正文
5. 评论区问题
6. 其它提示
7. 发布前自检（由 AI 录入时评判填写）

正文应包括可直接录制的第一人称稿件。事实与来源没有外部材料时，明确写成观点型内容，不要用空泛案例填充。用户没有给出时长时，按内容量估算，不宣称已经完成实际录音验证。

## 工作流

### 1. 生成草稿

1. 理解用户的主题、受众、说话位置和核心判断。先分开用户真实经历、外部材料和作者判断。选题方向尚不明确时使用 `selfmedia-topic-align`；个人风格按本文件开头的作者范围读取 `hongfenghua-ai-oral`，根据本期题材选择讲解方式，不预定观点或结尾。信息已经充分或用户只改局部时不重复对齐。若用户只要记录一个选题，先整理边界清楚的主题草案，不擅自扩成长稿；写文件或飞书按用户明确的保存意图处理。用户已要求写稿且信息足够时继续完成正文，不停在选题卡等待确认。
2. 需要当前产品、新闻、政策、数据或外部案例时，先研究并记录来源；只凭用户材料和个人判断时，明确事实边界。
3. 按 [template.md](references/template.md) 输出完整结构。`内容状态` 默认写“初稿”；示例稿写“示例，待确认”。
4. 外部材料带有清单或分论点时，先做素材熔炼。正文默认围绕一个主问题自然推进，不保留原结构作为隐形目录。先让问题、动作和判断出现，再补解释。控制句子长度，适合耳朵而不是只适合屏幕阅读。
5. 用“断言、重复、形象”做传播性自检：确认核心判断足够明确，核心词句有必要的稳定重复，抽象观点有真实的可见承载物。检查它们是否共同服务于复述，不用绝对化口号替代事实和依据。
6. 最后使用 `human-writing` 复核表达、虚构亲历和未核验事实。`hongfenghua-ai-oral` 激活时按其修辞规则人工审阅，不用通用 `check_prose.py` 的修辞失败项要求清零；其他稿件仍按通用检查流程执行。任何文字检查均不等同于实际试录。
7. 再做口播结构验收。去掉编号和小标题检查能否自然接续，确认段落没有按同一模具展开，具体场景有信息来路，作者的判断在正文中确有推进。任一项不成立时先重写结构，不用口头填充词修补。
8. 最终稿只输出模板内容，不输出内部提纲、检查过程或规则解释。字段按模板的标签行和自然段呈现，不把整篇稿件改成无关的清单。
9. 用户明确要求暂存时，将当前版本保存到临时目录；没有暂存或正式保存指令时，继续只在对话中输出。

### 2. 修改与确认

- 修改前读取 [口述与反馈改稿](references/revision-workflow.md)，以用户最新指定稿件为基准，判断反馈涉及观点、结构、措辞还是事实，再执行对应范围的修改。
- 只改指定部分，保留模板栏目、事实边界和已认可内容。用户要求全文重构时执行全文重构；不要把局部认可误当成整稿确认。
- 用户没有明确要求暂存或正式确认前，不创建飞书节点，不覆盖已有文档，不发送“已入库”。
- 用户要求暂存时，创建或更新临时目录中的目标文档，内容状态使用“初稿”“待确认”或用户指定状态；不要因此生成正式稿。
- 用户明确确认后，先把最终正文状态改为用户指定状态。用户未指定时使用“待录制”，不要写成“已发布”，再按正式目录流程新建文档。

### 3. 写入飞书

跨窗口执行时使用下面这个项目 wrapper 的绝对路径；在项目目录内也只能使用 `./bin/lark-cli`。禁止使用裸命令 `lark-cli`，禁止升级、注销全局 CLI，禁止执行 `profile use`。

```text
<LOCAL_PATH>
profile: feishu-personal
space: 7667564356321676539
space name: 自媒体口播文案
temporary parent title: 临时口播稿-稿件
formal parent title: 7-8 月口播稿
```

按以下顺序操作，全部使用 wrapper 并显式使用 `--as user`：

1. 检查 wrapper 可执行，并运行 `whoami`。确认输出中的 `profile` 是 `feishu-personal`，身份是 `user`，token 可用。失败就停止，不切换全局 profile。
2. 用 `wiki +node-list --space-id 7667564356321676539` 获取根节点。精确找到标题为“口播稿模板”“临时口播稿-稿件”和“7-8 月口播稿”的节点，并读取当前模板正文。模板远程内容是写入时的最终依据；找不到或有多个同名节点时停止并报告。
3. 按保存意图选择父节点：暂存使用“临时口播稿-稿件”，正式确认使用“7-8 月口播稿”。列出所选父节点下的子节点，检查新标题是否重复。重复时停止，不自动加后缀制造重复文档；不要把临时目录中的空白节点当作模板或现成稿件。
4. 用 `wiki +node-create` 创建 `docx` origin 节点，传入真实 `space_id`、所选父节点 token 和最终标题。不要用 `docs +create` 后再猜路径。
5. 用 `docs +update --command overwrite --doc-format xml` 写入完整模板化正文。写入前读取 CLI 匹配版本的 `lark-doc` 更新规则和 XML 规则；不要把 XML 标签转义成文本。
6. 用 `docs +fetch` 回读新文档，至少核对标题、模板栏目、内容状态和“发布前自检（由 AI 录入时评判填写）”原文。再用 `wiki +node-list` 确认新节点的 `parent_node_token` 确实是本次选择的父节点。
7. 最终只报告真实创建结果和飞书链接，明确区分“已生成草稿”“已暂存临时稿”“已创建正式文档”“已回读验证”。

### 4. 写入失败

- 权限、profile、模板定位或父节点定位失败时，不在其他目录创建替代文档。
- 节点创建成功但正文写入失败时，报告新节点链接和失败阶段，不重复创建同名节点；后续修复应对该 `obj_token` 继续写入。
- 任何写操作返回不确定状态时，先回读目录和文档，再决定是否继续，避免重复创建。
