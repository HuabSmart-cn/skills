# Miora Creative Core

图片与视频生成的**执行底座**，所有创意媒体任务共用。只负责**怎么把事情安全、准确、不浪费地做完**：路由到正确的场景、把参数补齐、征求用户同意、选对生成工具、失败时不乱重试、产物能被下一步引用、产物落到画布交付、交付前验证到位。

## 适用与不适用

**适用**：交付物是 AI 生成的图片或视频。海报、详情图、logo、图标、吉祥物、插画、系列素材、短视频等。

**不适用**（遇到这些不要往下走）：
- **纯文字交付物** — 文案、脚本、方案、分析报告。这些不需要生成媒体。
- **确定性像素操作** — 裁剪、缩放、旋转、格式转换、压缩、拼接。这些是对原图像素的精确操作，用生成来做等于重绘画面，还要向用户收生成费用。明确说明这是像素操作，不要转成生成任务。

判断不了是否适用时，问用户，不要默认往生成走。

## 标准流程

| 步骤 | 做什么 | 相关参考 |
|---|---|---|
| 1 | 意图识别：定 domain skill、定场景 | — |
| 2 | 定参数、确认要产出什么 | `references/input-contract.md` |

| 5 | 全部产出后收尾：整批验收、写检查结论 | `references/quality-gates.md` |

## 一、开工先做意图识别

识别错了后面全错。两步：**先定 domain skill → 再定具体场景**，两步都是互斥的单选。

### 定 domain skill

| 交付物 | 去向 |
|---|---|
| 品牌资产 — Logo、品牌吉祥物 / IP 角色、品牌 VI 全案、IP 周边与材质系列 | `miora-brand-design` |
| 其他静态图片 — 电商详情图、App 图标、海报、插画、游戏角色原画、单张带 logo 的图 | `miora-image-generation` |
| 会动 / 会响的 — 视频、动效 | `miora-video-generation` |

**先看是不是品牌资产，不是才按媒体形态分。** 分界在于**要不要跟一整套品牌资产保持一致**：品牌全案里也有图，但那些图受品牌设计系统约束，和随手做一张海报不是一回事。只是单独一张、不涉及品牌一致性 → 图片层；**App 图标也走图片层**，它有自己一套系统约束。

### 定具体场景

判断依据的优先顺序：**用户明确说了什么** > **附件类型** > **语义推断**。

- **明确信号优先** — 用户说了"亚马逊 A+"、"logo"、"吉祥物"、"app 图标"，就按它走，不要自作聪明改判。
- **附件是强信号** — 产品实拍白底图 + 提到电商 / 详情页 / 卖点，基本就是电商详情图场景。
- **相邻场景要划清** — 场景 reference 开头写了范围边界的，用它来排除。典型易混：电商详情图 vs 轮播主图 vs listing 文案；app 图标 vs logo vs UI 图标集；品牌全案 vs 单个品牌物料。
- **判断不了就问，不许猜。** 尤其当候选场景的产出规模差很多时（品牌全案 5+ 张 vs 只做 logo 几张），猜错会让用户白花钱。
- **场景是单选的** — 一轮只走一个场景，不要同时套两套流程。
- **再单独判断一次这批产物要不要读起来是一套**（同一主体反复出现、统一风格系列、同一标记的多个状态）。是一套就要在场景流程之外，按 domain skill 的 references 索引再加载一致性能力——它和场景不是二选一。没命中任何场景时（用户只说"来几张风格一致的图"）同样要判断。

### 中途换场景

用户在对话中途转向另一个场景时（做完 logo 说"再帮我做套详情图"）：**按新需求重新做一次意图识别**，不要用旧场景的流程套新需求，也不要在一轮里同时跑两个场景。旧场景已确认的产物（如已定稿的 logo）可以作为新场景的输入，见 `references/output-contract.md` 的风格锚点。

## 二、生成前确认与费用边界

媒体生成是**收费操作**，属于敏感动作。每次发起生成之前，必须用 `AskUserQuestion` 提问，等用户答复后再发起生成。

### 参数怎么定

能不问就不问，只问关键的

| 参数性质 | 怎么处理 |
|---|---|
| 有合理默认值 | 直接用默认值，不要问，但定下来的值要写进这次确认里展示出来 |
| 会改变整份产出结构 | 必须明确；不明确就问。这类参数决定后面每一步（视频类型决定整个分镜结构、品牌任务范围决定产出 5 项还是 1 项），**不许猜** |
| 用户已经说了 | 原样跟随，不要"优化" |

用户带了附件或参考素材时，先读 `references/input-contract.md`。

### 确认里要写什么

这一步要用户点头的不是风格偏好，而是**这次到底要产出什么**。问题正文里要让用户看清下面三项，只做一件时同样要写全：

- 产出什么、多少个。 会产出多个资产、而用户没有明确要求这个规模时，还要把更轻的做法做成并列选项——例如用户只说"帮我做品牌设计"，要告知全案是 5+ 张、分多批推进，同时给出"只要 logo"这个选项。
- 本次的规格。画幅、尺寸、时长——包括你自己按默认值定下来的那些。
- 会用到的素材。 用户给的参考图、上一轮的锚点；一个都没用到也要说明是纯文字生成。

规格必须写在问题正文里，不能只放在某个选项的描述里。放进选项等于把规格绑死在那个选项上：用户想要"这个风格 + 另一个画幅"表达不出来，没被选中的那几种规格也从头到尾没人看见。

**展示不等于追问。** 按默认值定下来的参数照样要展示，用户不反对即生效——不要因为"这项有默认值"就不写，也不要为每个默认值单独开一个问题。真正需要用户拍板的维度才做成选项；有多个维度要拍板时 `AskUserQuestion` 支持一次问多个问题，一个维度一个问题，不要把两个维度压进同一组选项。

### 什么时候问

- **一批一次。** 开工前对整批问一次，同意后把这一批做完，**批内不再逐张追问**。
- 需要**重新问**的情形：产出规模超出已确认范围、关键参数发生实质变化、用户要求重做或改稿、进入此前未被确认的下一批。
- 场景 reference 明确要求逐项定稿参数时（如品牌锚点），**按 reference 走**，这类业务确认不被"整批已同意"覆盖。

## 三、选哪个生成工具

判断看手上有没有可用的素材，以及那份素材扮演什么角色：

| 手上有什么 | 交付 | 走哪个 |
|---|---|---|
| 只有文字 | 图 | `mcp__miora__miora_text_to_image` |
| 只有文字 | 视频 | `mcp__miora__miora_text_to_video` |
| 有图，要改它 / 以它为基准派生 | 图 | `mcp__miora__miora_edit_image` |
| 有图，要它当视频的起始画面（可另给结束画面） | 视频 | `mcp__miora__miora_frame_to_video` |
| 有图，要它锚定视频里的主体或风格 | 视频 | `mcp__miora__miora_reference_to_video` |

- 只用这张表里的工具。运行时可能同时存在别的图片 / 视频生成工具（如 `ImageGen`、`VideoGen`），**本 skill 的场景一律走 `mcp__miora__*`**。
- **有素材就绝不走纯文字工具。** 用户给的参考图、已确认的锚点、上一轮的定稿都是硬约束。走纯文字工具就等于把它们退化成提示词里的文字描述，拿到的是「像但不是同一个」的东西——一致性正是在这一步丢掉的，而且这次无效生成要用户付费。领域 skill 里"不能用文字描述替代参考图"说的就是这件事。
- 这里说的「有素材」指手上有实际文件。产物引用怎么维护见 `references/output-contract.md`。

## 四、拿到一件就写进画布

判据只有一个 —— 这件产物成功拿到本地文件了没有。拿到了就立刻写进画布。具体调用见 `references/canvas-delivery.md`。

本 skill 覆盖的所有场景，产物都落到**一张** `.miora` 画布上：首件 `create`，之后一律 `update`。

---

## 五、收尾

这一批全部产出之后，按 `references/quality-gates.md` 做整批验收，再把结论写给用户：

- 逐件检查 — 内容对不对得上诉求、实际规格与确认过的是否一致。只做了一件也要做。
- 成套检查 — 画幅是否逐张统一、一致性是否成立、有没有几乎重复的产物。
- 写检查结论

⚠️ **不合格不要自动重做**，是否重做由用户决定。

## 对外表达

- **用设计语言说话**，不要暴露内部机制：比如说"生成图片"而不是"调用工具"
- **不要暴露**字段名、模型标识、任务 id。
- 用户可见文案与向用户提问使用**同一种语言**：优先用户明确要求的语言，否则跟随用户当前使用的语言。
- **简明。** 生成类任务的价值在产出物本身，不需要长篇解释过程。
